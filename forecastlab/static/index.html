THE FORECASTLAB APPROACH

Useful forecasts start with honest evaluation.

ForecastLab models daily, nonnegative demand. It works with sales, web traffic, service requests, or similar series. It does not infer business context, holidays, promotions, or stockouts from a value alone.

Validate→Select→Calibrate→Test→Refit→Plan

Four candidates, the same forecast windows

Seasonal naive repeats the last week. Moving average uses the latest 28 available values. Ridge regression and XGBoost use lagged values, trailing statistics, calendar features, and a time index. All multi-day predictions are recursive: predicted values, never future actuals, become the history for later steps.

Selection is separate from the final test

Three expanding-window folds select a model per series by MAE. Two later folds estimate an absolute-error interval width. The final horizon is reserved for holdout evaluation. Models are then refit on all history to produce the next forecast. Settings are fixed rather than optimized against the holdout.

Intervals are estimates, not promises

The nominal 80% band uses a finite-sample corrected quantile of absolute errors from the two calibration folds. Errors are pooled across lead times within each series. Time dependence, limited calibration data, distribution shifts, and refitting can reduce future coverage. The dashboard reports observed holdout coverage alongside the nominal level. Daily bands cannot be summed into a valid total-demand confidence interval.

Metrics with clear meanings

MAE is the mean absolute error in the series’ units. WAPE is total absolute error divided by total actual demand; it is undefined when total actual demand is zero. RMSE gives large errors more weight. Bias is average prediction minus actual. Coverage is the proportion of holdout observations inside their predicted bands.

Planning assumptions stay visible

The capacity scenario assumes fixed daily capacity, with no carry-over. Inventory uses expected demand across lead time plus review period, plus a user-entered safety stock, minus inventory position. These scenarios do not establish cost savings or a probabilistic service level.

Built for a local portfolio workflow

SQLite runs by default; PostgreSQL is supported through Docker Compose. Training uses a single application process. Optional MLflow logging and explicit S3 exports are available through configuration and the CLI. This local application has no user authentication; add access controls and a durable worker queue before a shared production deployment.
